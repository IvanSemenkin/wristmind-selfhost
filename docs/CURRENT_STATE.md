WristMind состоит из четырёх активных поверхностей:

| Часть | Назначение |
| --- | --- |
| `server/` | FastAPI, PostgreSQL/pgvector, worker, RAG, провайдеры моделей, API и SSE. |
| `web/` | Веб-панель управления на `https://wm.xspase.ru`. |
| `android/wear/` | Основной самостоятельный клиент Xiaomi Watch 2. |
| `android/phone/` | Минимальный companion: настройка/статус и fallback через Wearable Data Layer, без собственного чата. |

Основной транспорт часов — прямой HTTPS. При настоящей транспортной ошибке `FailoverWearGateway` переключается на companion через Wearable Data Layer; этот канал может использовать Bluetooth **или Wi-Fi**, поэтому его не следует называть гарантированно Bluetooth-каналом.

- Этап 1: перед веб-поиском формируется неизменяемый Request Anchor. Его фактические поля проверяются как дословные фрагменты исходного вопроса; повторный поиск требует типизированную retrieval-цель, а финальный prompt закрепляет исходную постановку над трактовками выдачи.
- Этап 2: компактный local-first Router выбирает `none`, `chat_sources`, `web` или `deep_web` после проверки истории, chat-scoped sources, базы режима и уже использованных ссылок. Research остаётся отдельной проверкой качества ответа и больше не включает интернет принудительно.
- Этап 3: каждая переданная модели веб-ссылка сохраняется как лёгкий Referenced Source; целый значимый материал при необходимости автоматически становится Working Source, изолированным текущим чатом. На этом новая цепочка заканчивается: межчатовые материалы по-прежнему обслуживает отдельный существующий механизм. Working Sources ранжируются, а не безусловно добавляются в prompt.
- Этап 4: для Working Source сохраняются raw cleaned page, URL, заголовок, хеш и границы происхождения. В RAG попадает только дословно проверенный извлечённый фрагмент; несовпавшее извлечение безопасно откатывается к полному очищенному тексту.
- Этап 5: на часах остались два понятных режима — AUTO и RESEARCH. AUTO передаёт выбор источников router'у, RESEARCH добавляет обязательную проверку ответа, но не заставляет использовать интернет. Проверка учитывает тип задачи: работа по тексту, актуальный факт или вычисление.

## Изменения 1 октября — временный дубль вопроса после fallback-синхронизации

- После добавления резервного режима один отправленный вопрос мог временно отображаться на часах двумя пользовательскими пузырями во время генерации. Проверка production-базы и request ID показала, что сервер сохранял только один вопрос и один ответ: дубль существовал только в Wear-интерфейсе.
- Причиной была гонка между локальным оптимистичным вопросом и `state_changed`-обновлением. После синхронизации fallback-кеша идентификатор сообщения до отправки мог уже не совпадать с серверным, поэтому загруженная пара `user + пустой streaming assistant` не всегда замещала локальную копию.
- `pendingServerUserIndex` теперь распознаёт завершающую серверный список пару `user + пустой streaming assistant` как уже принятый pending-turn даже при сменившемся baseline ID. Завершённые старые пары под это правило не попадают.
- Добавлены регрессионные тесты для fallback-cache migration и нового вопроса после завершённого ответа. Полный `:wear:testDebugUnitTest` и `:wear:assembleDebug` прошли под JDK 21. Исправленный APK установлен на Xiaomi Watch 2 через беспроводной ADB.

## Изменения 1 октября — выдача кода подключения на слабой сети

- Production-логи подтвердили, что при неудаче в школе запросы панели доходили до API и завершались `201 Created`, но ответы терялись на слабой мобильной сети. Повторные нажатия создавали новые коды, тогда как интерфейс продолжал показывать пустое состояние.
- `POST /v1/devices/pairing-codes` теперь принимает необязательный `client_request_id`. Повтор с тем же ID возвращает тот же шестизначный код и срок действия. Код детерминированно восстанавливается через серверный pepper; открытый код по-прежнему не хранится в базе. Старые клиенты без request ID остаются совместимыми.
- Web-панель ограничивает одну попытку 12 секундами, автоматически повторяет сетевой сбой до трёх раз с тем же ID и объединяет одновременные запросы. После неоднозначной ошибки ручной повтор использует тот же ID до десяти минут. Действующий код не исчезает из интерфейса, пока новый не получен.
- Диалог показывает постоянную inline-ошибку и кнопку «Повторить», а не только краткий toast. Локальный и VPS production build прошли; API и web развёрнуты, внешний `/health`, `/settings` и `/fallback/health` отвечают успешно. Полный серверный прогон: 50 тестов прошли.

## Изменения 28 сентября — предложение сохранить найденный материал

- Открытая при исследовании веб-страница может стать кандидатом на сохранение, только если отдельная консервативная проверка считает её опорным материалом для продолжения именно этого диалога. Обычные разовые ссылки, новости, сниппеты и короткие страницы не предлагают сохранять.
- После готового ответа часы показывают одну карточку «Сохранить в этот чат?» с названием, коротким фрагментом и кнопками ✓/X. Никакого автосохранения нет; очередь нескольких предложений показывается по одному.
- При ✓ текст копируется в изолированный источник текущего чата и проходит обычную обработку для поиска по контексту. Он не отображается в общей базе режима и не доступен другим чатам. При X карточка скрывается. Если пользователь позднее явно попросит сохранить материал, последнее несохранённое предложение этого чата можно показать снова.

## Последняя неисправность и локальный фикс

### Наблюдение пользователя

21 сентября примерно в 13:20–13:40 МСК часы иногда создавали чат, но отправка сообщений сразу сбрасывалась с красной точкой. В этот период сервер получал health-check и создание чата, но часть `POST /v1/chats/{id}/messages` вообще не доходила. Значит это был локальный сбой маршрута часов/companion до API, а не ошибка ИИ или сервера.

### Подтверждённая причина в коде

Для сообщений действовали три несовместимых дедлайна:

1. прямой путь ожидал 1,2 секунды, затем переключался на companion;
2. RPC через companion отменялся через 8 секунд;
3. `WearViewModel` отменял всю отправку уже через 10 секунд.

При этом HTTP-клиент companion допускает до 15 секунд только на подключение к мобильной сети. Поэтому корректный запрос мог быть отменён на часах до того, как телефон успевал отправить его на API. Создание чата не имело такого общего десятисекундного потолка, что объясняет различие поведения.

### Внесённый фикс

- `android/core/.../ProxyProtocol.kt`: `RPC_TIMEOUT_MS` увеличен с 8 до 25 секунд.
- `android/wear/.../WearViewModel.kt`: снят дополнительный глобальный `withTimeout(10 seconds)` вокруг `gateway.sendMessage`; каждый маршрут использует собственный транспортный дедлайн.
- Прямой быстрый путь не менялся: через 1,2 секунды он по-прежнему переключается на companion. Сохранённый `client_request_id` предотвращает дубли при повторе.

Проверка локально прошла под JDK 21:

```text
:core:test :wear:testDebugUnitTest :wear:assembleDebug :phone:assembleDebug
BUILD SUCCESSFUL
```

Wear APK с фиксом установлен на подключённые часы 21 сентября. Companion APK собран и отправлен пользователю в его Telegram-бот. **Пользователь должен установить обновлённый companion на телефон перед проверкой**, иначе на телефоне останется старый 8-секундный лимит и фикса не будет на fallback-маршруте.

Собранные debug APK (не добавлять в Git):

- `android/wear/build/outputs/apk/debug/wear-debug.apk`
- `android/phone/build/outputs/apk/debug/phone-debug.apk`

Следующая обязательная проверка после установки обоих APK: создать чат и отправить несколько сообщений с часов на мобильной сети при соединении с телефоном. Следить, что сообщение либо быстро принимается, либо остаётся в отправке/повторяется тем же request ID, но не получает красную ошибку до истечения реального транспортного бюджета.

## Важные эксплуатационные заметки

### Telegram bot (27 сентября)

- The bot is restricted to the configured Telegram owner ID. Production delivery uses the dedicated `telegram-bot` long-polling service: both `getUpdates` and outgoing Bot API calls go through the restored AmneziaWG VPN. The webhook route remains in the API for compatibility, but the Telegram webhook is disabled because Telegram repeatedly timed out while connecting to the public endpoint.

- The route-fix service maintains a DNS-refreshed `wristmind_telegram` ipset and marks Telegram traffic from the backend subnet for VPN table 51821. Verification after deployment: Bot API returned HTTP 200 from both API and worker, polling consumed the pending queue to zero, and the Telegram route packet counter increased.
- Text and photo handlers flush a newly created job before inserting its initial `JobEvent`; without that flush PostgreSQL received a null `job_id`, rolled the transaction back, and the consumed Telegram update produced no reply.

### Worker recovery (27 сентября)

- A worker crash could leave a claimed job permanently in `running`; the next worker ignored it. `recover_interrupted_jobs()` now returns such jobs to `queued` at worker startup. This recovered an OCR ingestion job that had been stuck after the worker import failure.
- Transient OpenRouter embedding connection failures no longer leave an uploaded document in terminal `failed`: ingestion is requeued with exponential backoff (30 seconds to 15 minutes, at most eight retries), while delayed retries do not block answer jobs. Embedding connection setup is limited to 10 seconds instead of occupying the only worker for the previous 120-second timeout.
- The 27 September ingestion failure had two operational causes. The worker was first deployed with mismatched source files and failed on an import; after that was corrected, the Orange Pi AmneziaWG client still referenced the VPN server's old peer key and old UDP port. The current VPN server listens on UDP 38363 and had been recreated without the Orange Pi `10.8.1.4` peer. The peer and matching client configuration were regenerated, the handshake and `GET https://openrouter.ai/api/v1/models` from the worker were verified, and the failed document was requeued. Final state: source `ready`, 10 pages, 10 chunks, 6349 estimated tokens.

- Backend развёрнут отдельно от web. Для API/worker используется Orange Pi и Docker Compose; web-панель живёт на VPS как systemd-сервис. Перед любым деплоем сначала проверить состояние конкретной машины и активный checkout, а затем health-check снаружи.
- У backend есть reverse SSH tunnel от Orange Pi к VPS. Не менять маршрутизацию, VPN или правила NAT без проверки OpenRouter из **worker-контейнера**, а не только с хоста.
- OpenRouter в production проходит через VPN-маршрут и использует `curl-cffi` с профилем Chrome. Раньше неверная VPN-таблица вызывала `403 Access denied by security policy` именно из worker.
- После пересоздания API/worker перезапускать nginx compose-сервиса и проверять `/health`; иначе nginx иногда продолжает резолвить старый IP контейнера.
- На сервере есть устаревшие FCM-регистрации: их отправка логирует `NotRegistered`. Это не объясняет отказ POST-запроса, но пуши нельзя считать надёжным способом доставки ответа, пока устаревшие токены не будут корректно очищены/диагностированы.

| Медленные ответы | `worker.process_answer` → `providers.ProviderRouter` и логи worker. |
| Не приходят ответы на часы | FCM рассматривать только как сигнал; затем проверять job events, прямой API и Data Layer. |
| Новая web-панель | `web/src/app/App.tsx` → `web/src/services/ApiWristMindService.ts` → `web/src/store/clientStore.ts`. Старые `web/components/wristmind/control-panel.tsx` и `web/lib/wristmind-api.ts` сохранены в рабочем дереве как неиспользуемый прежний интерфейс до отдельной уборки. |

### Панель: устройства и промпты (4 октября)

- На странице устройств видны браузер/ОС, короткий ID и последний публичный IP, когда он известен. Отозванную запись можно убрать из списка; строка остаётся в БД для истории.
- Нижний пункт «Обзор» подсвечивается на `/main`.
- Системные и внутренние промпты вынесены из настроек на страницу «Промпты». Она видна в боковой навигации и мобильном «Ещё» только при включённом режиме разработчика. Промпты режимов остаются доступными для редактирования в каждом режиме всегда, а при включённом режиме разработчика показаны и на общей странице.

- API и worker опубликованы на `my-server-global`, панель и резервный сервис — на VPS. Публичные `/health` и `/main` отвечают 200; резервный сервис отвечает `status: ok`.
