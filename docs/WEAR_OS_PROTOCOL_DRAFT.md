# WristMind Wear OS: протокол и аудит v0

Статус: рабочий черновик первого этапа. Документ относится только к новому
модулю `android/wear`. Legacy-реализация в `watch/` и старый BLE-документ
`docs/PROTOCOL.md` не изменяются.

## Что уже есть

### VPS API

- `POST /v1/devices/pairing-codes` — админ создаёт одноразовый код на 10 минут.
- `POST /v1/devices/enroll` — часы обменивают код на device token.
- Защищенные запросы используют `Authorization: Bearer <device token>`.
- `GET /v1/modes` и `GET /v1/chats` — синхронизация режимов и чатов.
- `POST /v1/chats` — создание чата в выбранном режиме.
- `GET /v1/chats/{id}/messages` — загрузка сообщений.
- `POST /v1/chats/{id}/messages` — постановка вопроса в очередь. Поле
  `client_request_id` обеспечивает повторяемость без дублирования запроса.
- `GET /v1/jobs/{id}` — состояние фоновой задачи.
- `GET /v1/jobs/{id}/events?after=N` — SSE-поток событий задачи с курсором.
- `POST /v1/stt` — принимает готовый аудиофайл. Потокового endpoint пока нет.

События ответа: `state` (`context`, `generating`), `delta`, `complete`,
`error`. В `delta` приходит фрагмент полного ответа, поэтому часы должны
накапливать текст, а не ограничиваться одной строкой.

### Новый Wear OS-модуль

В `android/wear` уже есть Compose-заготовка, авторизация и выбор режимов/чатов.
`WearSpeechRecognizer` использует системный `SpeechRecognizer` с частичными
результатами на `ru-RU`; после финального текста `WearViewModel` создаёт чат,
отправляет сообщение и читает SSE-события.

Device token хранится через `EncryptedSharedPreferences` в общем `core`-модуле.
Приложение объявлено standalone для Wear OS и имеет разрешение микрофона.

## Что пока не готово

1. Системное распознавание не гарантирует русский язык и может зависеть от
   доступности сетевого сервиса на часах; это не заменяет запись микрофона и
   серверный STT.
2. `/v1/stt` работает только после окончания записи. Для потоковой передачи
   нужен отдельный endpoint/протокол и резервная отправка готового файла.
3. Прямой HTTPS-канал часов и Bluetooth-прокси телефона пока не разделены
   общей транспортной абстракцией.
4. В новом модуле ещё нет тестового fake-transport, проверки восстановления
   SSE и измерения всех этапов задержки.
5. `android/phone` и `android/wear` сейчас используют один `applicationId`;
   перед публикацией нужно отдельно проверить стратегию установки и при
   необходимости разделить идентификаторы.

## Целевой контракт состояний

```text
READY
  -> LISTENING       старт записи
LISTENING
  -> RECOGNIZED      получен финальный текст
  -> ERROR           ошибка микрофона/распознавания
RECOGNIZED
  -> SENDING         отправка вопроса
SENDING
  -> CONTEXT         сервер выбирает контекст/RAG
  -> GENERATING      модель начала ответ
  -> ERROR           сеть, авторизация или провайдер
CONTEXT/GENERATING
  -> COMPLETE        пришёл complete и полный ответ сохранён
ERROR
  -> SENDING         повтор того же client_request_id или новый запрос
  -> READY           сброс
COMPLETE
  -> READY           новый вопрос
```

Для каждого запроса сохраняются `request_id`, `job_id`, `mode_id`, `chat_id`,
время старта записи, время остановки, отправки, первого токена и завершения.

## Транспорт

Первый MVP использует прямой HTTPS с часов на VPS. Позже тот же контракт
получает две реализации:

- `DirectHttpTransport` — Wi‑Fi часов → VPS;
- `PhoneProxyTransport` — часы → Wearable Data Layer/Bluetooth → приложение
  телефона → VPS.

Решения о точном поведении кнопок, максимальной длительности записи, отмене,
режимах отображения расшифровки и навигации по чатам принимаются перед UI-этапом.

## Следующий безопасный шаг

Добавить fake-transport и контрактные тесты для pairing, синхронизации режимов,
создания чата, отправки сообщения, SSE-событий, повторов и ошибок. После этого
согласовать MVP-функции часов и только затем менять `android/wear` UI/запись.
