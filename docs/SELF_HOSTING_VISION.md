# WristMind — видение self-hosting

Это документ о **том, каким должен стать продукт для стороннего человека**, а не описание того, что уже работает. Фактическое состояние — в [CURRENT_STATE.md](CURRENT_STATE.md), устройство системы — в [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md). Ничего из этого пока не реализовано.

Цель: любой человек берёт репозиторий, ставит сервер себе за десять минут и подключает часы — без Google Play, без ручного adb с ноутбука и без чтения внутренней документации.

Три раздела: **сервер**, **приложения на телефоне и часах**, **управление сервером**. Последний раздел описывает повторный запуск установщика — это отдельный пользовательский сценарий, а не деталь реализации.

## 1. Точка входа: страница репозитория

Первый экран README должен отвечать на три вопроса и ничего не обещать лишнего:

- **Что это:** ассистент на часах Wear OS. Голосовой чат, режимы, свои базы знаний. Ставится на свой сервер, данные остаются у владельца.
- **Что понадобится** — до клика, честным списком:
  - часы Wear OS (Xiaomi Watch 2 проверены, остальные — по возможности);
  - сервер или VPS: 2 vCPU, 4 ГБ RAM, 10 ГБ диска;
  - домен (для HTTPS без него часы не подключатся);
  - ключ провайдера модели: OpenRouter или DeepSeek; оплата — на владельце;
  - Wi-Fi, где на момент установки телефон и часы в одной сети.
- **Чего не нужно:** Google Play, аккаунтов в сторонних сервисах, VPN, ручного adb с ноутбука.

Далее — три пути: `Установить сервер`, `Скриншоты`, `Документация`. Схема «сначала клонируй репозиторий» первым шагом быть не должна.

## 2. Сценарий: установка сервера

### 2.1. Выбор места

Меню из трёх вариантов, потому что людей трое:

- **Сервер или VPS** (основной путь): один блок команд, без сборки из исходников.
- **Домашний сервер или мини-ПК**: то же плюс честное предупреждение, что сервер за NAT потребует проброса портов или обратного туннеля.
- **Локально, чтобы посмотреть**: `docker compose up` на ноутбуке, мок-данные, без ключей и без часов.

### 2.2. Требования к железу

Минимум — 2 vCPU, 4 ГБ RAM, 10 ГБ диска. В базовой конфигурации поднимаются **три контейнера**: `db`, `api`, `worker`. Всё остальное — опциональные профили:

- веб-поиск (SearXNG) — только если владелец его включил.

### 2.3. Установка

Одна команда. Скрипт печатает понятные шаги, а не молчит:

```
1/5 Загружаю конфигурацию
2/5 Поднимаю базу данных          ✅
3/5 Запускаю API и обработчик     ✅
4/5 Запускаю веб-панель           ✅
5/5 Готово → откройте http://<IP>:8080/setup
```

### 2.4. HTTPS и домен

Выпуск сертификата — **внутри продукта**, а не руками через certbot. Без HTTPS часы подключить нельзя, и об этом надо сказать на первом экране, а не в середине мастера. Если домена нет, сервер честно сообщает, что панель будет доступна по IP, а часы — нет.

### 2.5. Мастер первого запуска в браузере

Чек-лист с живой проверкой каждого пункта:

1. ✅ База данных и API запущены;
2. ⬜ админ-аккаунт (имя, пароль) — bootstrap-секрет из `.env` не должен быть виден пользователю вообще;
3. ⬜ ключ модели с кнопкой «Проверить», реальным дешёвым вызовом, оценкой стоимости и возможностью задать потолок расхода на день;
4. ⬜ первый режим: название, модель, промпт из шаблона, сразу загрузка источника;
5. ⬜ проверка: «Задать вопрос» прямо в мастере, до всяких часов.

Итоговый экран: адрес панели и адрес API.

### 2.6. Сервер за NAT

Отдельный шаг мастера: либо проброс портов на роутере с картинкой и полями, либо обратный туннель (сервер сам подключается к VPS, публичный адрес даёт VPS). Адрес VPS должен быть настраиваемым полем, а не зашитой константой.

## 3. Сценарий: подключение телефона и установка на часы

### 3.1. Телефон

- Компаньон ставится из Releases (Google Play не используется).
- Ввод: адрес сервера и вход. Штатный путь — логин и пароль из мастера, одноразовый код остаётся резервом.
- Компаньон подтверждает связь и показывает статус сервера.

### 3.2. Ограничения, которые нельзя обойти

- **Компаньон не может включить на часах режим разработчика и отладку по ADB.** Это системные настройки часов; включаются только физически на самих часах. `WRITE_SECURE_SETTINGS` у компаньона меняет настройки телефона, а не часов.
- **Data Layer доставляет данные только приложению, которое уже установлено на часах.** «Нулевой» установщик по воздуху приехать не может — его самого ещё нет.

Отсюда единственный принятый путь: **человек вводит в компаньон адрес и порт часов, компаньон сам заливает APK и сам передаёт настройки.**

### 3.3. Мастер установки на часы (шесть экранов)

**Экран 1. Состояние.** Главный экран компаньона: телефон подключён, блок «Часы — не подключены», кнопка «Подключить часы».

**Экран 2. Инструкция.** Единственное место, где человек действует руками:

1. Настройки → О телефоне → Номер сборки — нажать 7 раз;
2. Настройки → Для разработчиков → Отладка по ADB — включить;
3. Часы покажут адрес и порт вида `192.168.0.218:37267`. Эти два значения надо ввести в компаньон.

**Экран 3. Адрес часов.** Два поля — адрес и порт. Порт обязателен: на Wear OS он назначается динамически и меняется после перезагрузки. Кнопка «Проверить связь» до установки, с честным результатом и тремя причинами отказа: часы в другой сети, отладка не включена, неверный порт.

**Экран 4. Установка.** Прогресс по шагам, а не одна вертушка:

```
1. Связь с часами          ✅
2. Отправляю приложение    ▓▓▓▓▓░░░ 62%
3. Устанавливаю            ⏳
4. Настраиваю              ⏳
```

APK берётся либо со своего сервера (тогда обновление часов не требует новой сборки компаньона), либо из встроенной копии — человеку это не видно. Компаньон заранее предупреждает, что на часах может появиться системный запрос подтверждения установки.

**Экран 5. Передача настроек.** Чтобы на часах ничего не вводить, компаньон передаёт адрес сервера и device-token:

1. через Data Layer — канал `/wristmind/config/v1` уже существует, часы его слушают и принимают только записи с `origin: "phone"`;
2. запасной путь — запись конфига напрямую в приватное хранилище приложения на часах по ADB (тот же `DeviceConfigStore`), требует хотя бы одного запуска приложения на часах;
3. крайний случай — экран ручного ввода адреса и кода на часах.

**Экран 6. Финал.** «Часы подключены», версия, адрес сервера, подтверждение, что устройство видно в панели. Компаньон сохраняет адрес часов и версию, чтобы потом предлагать «Обновить» без повторного ввода.

### 3.4. Повторные сценарии

- **Обновление приложения на часах**: та же последовательность, настройки не трогаются.
- **Сменился адрес сервера**: конфиг обновляется по Data Layer или ADB, переустановка не нужна.
- **Сменился порт отладки**: компаньон сам замечает, что старый не отвечает, и просит новый.
- **Вторые часы**: тот же мастер, отдельный код, отдельный device-token, отдельная запись в панели.
- **Отвязка часов**: токен отзывается на сервере, а не только локально.

### 3.5. Что для этого нужно

- Встроенный ADB-клиент в компаньоне (dial `ip:port`, install, shell) — единственная принципиально новая зависимость.
- Доступность APK часов компаньону: лучше с сервера, чем в сборке.
- Проверка совместимости до заливки: версия Wear OS против `minSdk`, иначе пользователь получит невнятную ошибку.
- `/wristmind/config/v1` как задокументированный контракт с версией и правилами совместимости.
- Нейтральный адрес сервера по умолчанию в сборках приложений — без домена владельца репозитория.
- Неизменность ключа подписи: обновление «поверх» работает только с той же подписью.

## 4. Сценарий: управление сервером с меню

Установщик должен быть идемпотентным: повторный запуск **не начинает установку заново**, а открывает меню управления. Это отдельный пользовательский сценарий, а не деталь реализации.

### 4.1. Скрипт сначала определяет состояние

Проверяет: каталог установки, контейнеры, `.env`, домен и сертификат, версию. Ничего не находит — показывает меню установки. Находит — показывает меню управления. Первый экран установки больше никогда не появляется молча.

### 4.2. Чистая машина

```
WristMind · установка

Сервер пока не установлен.

  1) Установить
  2) Проверить требования (Docker, память, порты)
  3) Что это и что понадобится
  0) Выход
```

### 4.3. Уже установлено

```
WristMind · управление                       версия 0.1.0 · обновлений нет

  Сервер:   работает (запущен 3 дня)
  Адрес:    https://мой-домен.ru
  Домен:    мой-домен.ru · HTTPS ✅
  База:     PostgreSQL ✅   Источники: 12   Чатов: 8

  1) Обновить до последней версии
  2) Проверить состояние (здоровье, логи, порты)
  3) Домен и HTTPS          → добавить / сменить / продлить
  4) Ключи и провайдеры     → ключ модели, веб-поиск
  5) Резервные копии        → создать / скачать / восстановить
  6) Перезапустить
  7) Остановить
  8) Удалить установку
  9) Показать доступы (панель, API, коды подключения)
  0) Выход
```

### 4.4. Что делает каждый пункт

- **Установить** (только на чистой машине): требования → генерация секретов → три контейнера → адрес и статус. Спрашивает домен и ключ; ключ можно отложить и ввести в панели.
- **Обновить**: проверка версии → автоматический бэкап без вопроса → загрузка → пересборка → перезапуск → проверка здоровья → при провале автоматический откат с объяснением.
- **Проверить состояние**: здоровье API и обработчика, логи, занятые порты.
- **Домен и HTTPS**: добавить, сменить, продлить; честный отказ, если DNS ещё не указывает на сервер.
- **Ключи и провайдеры**: то же, что в мастере первого запуска, но доступное в любой момент, с живой проверкой ключа.
- **Резервные копии**: создать, скачать, восстановить. Должно быть видно и в скрипте, и в панели.
- **Перезапустить / Остановить**: безопасно; остановка не трогает тома с данными.
- **Удалить установку**: двойное подтверждение, автоматический бэкап и явный выбор между «только контейнеры и образы» и «всё, включая данные и тома» со словом-подтверждением.
- **Показать доступы**: адрес панели, адрес API, как выпустить код для телефона и часов.

### 4.5. Правила меню

- Повторный запуск никогда ничего не ломает; каждый пункт идемпотентен.
- Меню работает офлайн; сеть нужна только конкретным действиям, и они об этом говорят.
- Секреты не печатаются: ключи маскируются, пароль базы не показывается.
- Всё, что можно сделать в скрипте, доступно и в панели — кроме случаев, когда панель недоступна; тогда скрипт является аварийным входом.
- Скрипт определяет состояние сам и не просит пользователя выбирать «ставлю впервые / обновляюсь».
- Для автоматизации — флаги: `wristmind install --domain=… --key=… --yes`, `wristmind update --yes`, `wristmind backup`. Меню для человека, флаги для робота.

## 5. Обновления, бэкапы и доверие

- **Обновление — кнопкой** и в панели, и в скрипте: бэкап, обновление, проверка здоровья, откат при провале.
- **Релизы, а не git-ветка.** Обновление должно работать с версией, а не тянуть случайный промежуточный коммит.
- **Бэкап виден пользователю**: где лежат данные (Postgres и приватные файлы источников) и как получить их одним архивом. Ответственность за хранение копий — на владельце, и об этом сказано прямо.
- **Диагностика в панели**: доступность API, обработчика и резервного сервера, время ответа, последние ошибки. Тот же `/health`, что использует скрипт.
- **Отвязка устройства**: потерянные часы отзываются в панели, и всё, что могло писать, больше не может.

## 6. Что нужно создать и доработать

Это рабочий список, а не обещание. Все утверждения о текущем коде проверены на момент написания: ссылки на файлы даны, чтобы потом было от чего отталкиваться. Порядок внутри разделов — от того, без чего сценарий не работает вовсе, к тому, что можно доделать позже.

### 6.1. Создать с нуля

**Установщик с меню (`wristmind`).**
Сейчас есть только `server/deploy/initialize-env.sh`: он генерирует секреты и сразу выходит, если `.env` уже существует. Ни состояния, ни меню, ни идемпотентности, ни пункта «удалить». Нужен новый скрипт-обёртка, который определяет состояние машины и открывает одно из двух меню (см. раздел 4).

**Мастер первого запуска в веб-панели (`/setup`).**
Страницы `setup` в панели нет вообще. Нужен маршрут и мастер: админ-аккаунт, ключ модели с живой проверкой, первый режим, тестовый вопрос. Пока это делается правкой `.env` и пониманием внутренностей.

**Автоматический HTTPS.**
Сегодня сертификаты выпускаются вручную (certbot), а конфиги nginx лежат по доменам (`deploy/vps/wm.xspase.ru.conf`, `wm.arlienix.space.conf`). Нужен выпуск и продление сертификата силами установщика, с одним доменом по умолчанию.

**Бэкап и восстановление.**
Не автоматизированы нигде. Нужны: создать копию (Postgres и приватные файлы источников), скачать архивом, восстановить из копии, показать, где копии лежат.

**Удаление установки.**
Не существует. Нужен пункт с двумя режимами (только контейнеры и образы / всё вместе с данными), автоматическим бэкапом и подтверждением словом.

**Релизы.**
Нет версионированных артефактов: обновление сейчас — это `git pull` ветки. Нужны релизы с номерами, из которых установщик умеет ставить и обновлять, иначе «обновить до последней версии» будет тянуть случайный промежуточный коммит.

**Самопроверка требований.**
Пункт меню «Проверить требования»: Docker и Compose, память, диск, свободные порты, доступность DNS. Сегодня человек узнаёт о нехватке ресурсов из падения контейнера.

**«Показать доступы».**
Нет места, где одним экраном видно адрес панели, адрес API и как выпустить код для телефона и часов.

**Миграция `public_base_url` и проверка домена.**
Установщик должен сам подставлять выбранный домен во все места, где он нужен, и проверять, что A-запись уже указывает на сервер, до выпуска сертификата.

**ADB-клиент в компаньоне.**
В `android/phone/` и `android/core/` нет ни строчки ADB: сегодня установка на часы делается вручную с ноутбука. Нужен встроенный клиент (dial `ip:port`, install, shell) — это единственная принципиально новая зависимость компаньона.

**Экраны установки на часы в компаньоне.**
Сейчас компаньон умеет только сопряжение и Data Layer: блок «Часы — не подключены», инструкция по включению отладки, поля адреса и порта, проверка связи, прогресс установки, финал с версией и предложением обновления. Всё это надо создать (см. раздел 3.3).

**Раздача APK часов.**
Компаньон должен брать сборку либо со своего сервера (тогда обновление часов не требует новой сборки компаньона), либо из встроенной копии. Сейчас такого механизма нет.

**Проверка совместимости часов.**
Перед заливкой сравнить версию Wear OS с `minSdk` приложения. Иначе пользователь получает ошибку установки без объяснения.

**Запись конфига на часы по ADB.**
Запасной путь, когда Data Layer недоступен: запись адреса и токена в приватное хранилище приложения на часах (тот же `DeviceConfigStore` в `shared_prefs`).

**Контракт конфиг-канала.**
Сейчас `/wristmind/config/v1` живёт только в коде (`WatchLink.kt` и `WearConfigService.kt`). Нужен документ с версией и правилами совместимости, потому что от этого канала теперь зависит первичная настройка.

**Проверка целостности релиза.**
Установщик должен уметь ответить, что именно он поставил: версия API, версия панели, версия схемы БД. Сейчас это негде посмотреть.

### 6.2. Доработать существующее

**`server/compose.yaml` — привести к трём контейнерам по умолчанию.**
Сейчас в нём жёстко зашито специфичное: `route-fix` с iptables и ipset для маршрутизации провайдера через VPN, адрес конкретного VPS в переменных туннеля, Telegram, SearXNG. По умолчанию должны подниматься только `db`, `api`, `worker`, а личное — быть опциональным.

**Сделано 4 октября:** по решению владельца VPN-маршрутизация, обратный туннель и Telegram удалены из продукта совсем, а не переведены в профили. Остались профили `plain` (HTTP-фронтенд) и `search` (SearXNG). См. `SELF_HOSTING_STATUS.md`.

**Секреты — убрать из ручного ввода.**
Bootstrap-секрет, пароли базы и ключи туннеля должны генерироваться установщиком или задаваться в мастере. Bootstrap-секрет в пользовательском сценарии вообще не должен быть виден.

**Адрес сервера в приложениях.**
`WRISTMIND_BASE_URL` подставляется в `BuildConfig` на этапе сборки (`phone/build.gradle.kts`, `wear/build.gradle.kts`). В пользовательской версии это значение должно быть нейтральным по умолчанию, а реальный адрес — приходить из мастера и Data Layer.

**`initialize-env.sh` — превратить в часть установщика.**
Он полезен как генератор секретов, но должен вызываться установщиком, а не быть самостоятельным шагом, о котором надо знать.

**`update-server.sh` — переписать под релизы.**
Сейчас он делает `git pull`, пересборку и `nginx -s reload`, без бэкапа и без отката. Для стороннего пользователя нужны: бэкап перед обновлением, проверка здоровья после, автоматический откат при провале.

**Панель — добавить раздел «Резервные копии».**
То же, что пункт меню, но в интерфейсе: создать, скачать, восстановить.

**Диагностика — вывести наружу.**
Трейс и проверка здоровья уже есть (`/health`, JSONL-трейс), но пользователь их не видит. Нужен экран «Здоровье» в панели и опрос того же `/health` из установщика.

**Публичный README.**
Сейчас первый экран описывает исторический MVP (`README.md`: Poco F6, Amazfit, «тестовый ответ сервера»). Нужен новый первый экран под раздел 1 — что это, что понадобится, чего не нужно.

**Установщик для локального запуска.**
Режим «посмотреть без сервера»: мок-данные, без ключей и часов. Сейчас для этого нужно знать, как включаются моки.

### 6.3. Проверить и вычистить перед публикацией

**История репозитория.**
`.gitignore` закрывает `.env`, `google-services.json` и `*firebase-adminsdk*.json`, но нужно отдельно проверить, что эти файлы и ключи туннеля **никогда не коммитились**: если попадали в историю, простое удаление из рабочего дерева ничего не решает.

**Скрипты, завязанные на текущую инфраструктуру.**
`server/deploy/update-server.sh` работает с конкретным путём и ключом деплоя; `deploy/vps/*.conf` содержат имена доменов. Это остаётся для твоей установки, но не должно попадать в пользовательский сценарий.

**Захардкоженные адреса и имена.**
Проверить, что нигде в пользовательских путях не осталось конкретного адреса VPS, домена и имён контейнеров твоей инсталляции.

## 7. Честные стопперы

- **Часы не работают без HTTPS.** Нет домена — сценарий «сервер и часы» не складывается. Это говорится до начала установки.
- **Модель платная.** Ключ и счёт — на владельце; молчать об этом нельзя.
- **Отладка по ADB на Wear OS.** На части моделей и прошивок TCP-отладка без провода может требовать предварительного включения по USB или быть недоступной. Проверять на реальных часах до того, как строить мастер.
- **Порт отладки не постоянный.** После перезагрузки часов он меняется; компаньон обязан быть готовым попросить новый.
- **Смена подписи APK** ломает обновления навсегда. Ключ подписи — часть продукта.
- **Поддержка железа.** «Проверено на Xiaomi Watch 2» — честное обещание. Обещать все Wear OS нельзя.
