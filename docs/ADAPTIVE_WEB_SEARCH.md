# WristMind Web Search 2.1 — Adaptive Concurrency

13 октября 2026. Реализовано локально в основном проекте и синхронизировано с SelfHost. Серверы и GitHub не обновлялись; серверные исходники читались только для безопасного переноса общих изменений поверх отличий копии.

## Что уже было и что добавлено

Сохранены SearXNG/внешние API SelfHost, SSRF/redirect/download ограничения, полный HTML, изолированная trafilatura, PDF/Vision, RawWebSource TTL, рабочие источники и RAG. В исходной версии был один HTML semaphore; загрузка/извлечение страницы и глубокий агент были последовательны. Добавлены общий admission-controller и ограниченное чтение пары страниц для сравнения. Количество worker остаётся прежним: один; задания не запускаются параллельно.

## Лимиты одного worker/event loop

| Операция | NORMAL | Свободные ресурсы | BUSY | CRITICAL |
|---|---:|---:|---:|---:|
| Поисковые запросы (SearXNG или SelfHost API) | 1 | 2 | 1 | 1 |
| HTTP-загрузки | 2 | 3 | 1 | 1 |
| HTML extraction | 1 | 1 | 1 | 0 |
| PDF text layer / rendering | 1 | 1 | 1 | 0 |
| OCR / Vision | 1 | 1 | 1 | 0 |
| LLM-планирование | 1 | 1 | 1 | 1 |
| Новая индексация | 1 | 1 | 0 | 0 |

Повышение сетевых лимитов требует >1400 MiB доступной памяти, CPU load ratio <0.6, отсутствия активной тяжёлой обработки и небольшой очереди. Не создаётся дополнительных запросов поиска ради использования свободного слота. Дополнительных вызовов модели ради параллельности нет.

## Ресурсы и backpressure

- Linux MemAvailable, cgroup v2/v1 memory limit/usage и ограничения родительских cgroup; используется минимальный доступный объём. CPU — loadavg / эффективное число CPU, с учётом cpu.max v2. Это показатель нагрузки, а не точный процент занятости CPU контейнера.
- NORMAL: >900 MiB; BUSY: 500–900 MiB; CRITICAL: <500 MiB. CPU ratio >=0.9 также даёт BUSY, >=1.5 — CRITICAL. Начальные пороги оставлены из задания: при существующем HTML child cap 256 MiB они оставляют запас для PostgreSQL/worker/прочих сервисов. Фактическое устойчивое давление на Orange Pi в этой задаче не измерялось.
- Восстановление требует +150 MiB и двух последовательных проб; CPU для выхода из CRITICAL <1.2, из BUSY <0.75. Пробы не чаще раза в 2 секунды, по обращениям активных/ожидающих операций и при наличии ожидающих заданий; фонового мониторинга в простое нет.
- Без доступных метрик — фиксированные стандартные лимиты без увеличения сетевой параллельности. Пороги/ожидание задаются WRISTMIND_RESOURCE_* в env; конфигурация проверяет critical < busy < free.
- Admission использует счётчики, FIFO по типу операции и Event; Semaphore не заменяется. Общая очередь ожидания максимум 32, ожидание ресурса максимум 10 секунд и дополнительно ограничено бюджетом поиска. Уменьшение лимитов не прерывает начатую операцию.
- ANSWER остаётся приоритетнее INGEST. В BUSY/CRITICAL INGEST не забирается из очереди. Если давление возникло после начала ingestion, ResourceUnavailable использует существующий ограниченный retry/backoff без удаления источника.

## Чтение пары и отмена

Только сравнение / запрос нескольких источников может читать одновременно два подходящих URL из существующей выдачи. Однозначный одиночный источник открывается один раз. Результаты регистрируются в исходном порядке, ошибка одного URL не уничтожает другой; завершённый результат сохраняется при истечении бюджета второго чтения. Повторные одинаковые URL исключаются существующим каталогом результатов; свежий кэш переиспользуется.

AsyncSession не используется конкурентно: cache lookup проходит последовательно, затем запускаются максимум две сетевые задачи; сохранение источника/кэша остаётся последовательным. HTTP-слот освобождается перед ожиданием HTML/PDF extraction. HTML остаётся в изолированном процессе; отмена/timeout убивает и дожидается процесса до освобождения слота. Speculative fetch не добавлен — для него нет подтверждённого выигрыша.

Для синхронных PDF/render/OCR функций используется собственный ThreadPoolExecutor максимум с двумя потоками. Слот принадлежит concurrent Future физической функции; отмена вызывающей coroutine не освобождает его до реального завершения. Контекст трассировки переносится в поток. Отмена/drain сетевых задач и очереди проверены локально.

Общий бюджет агента теперь строгий: старые open/save floor аргументы совместимо принимаются, но не добавляют время сверх deadline. Это намеренная смена прежнего поведения: медленное сохранение может завершиться частичным результатом вместо продления поиска.

## Диагностика

Существующий privacy allowlist расширен только числовыми счётчиками и короткими кодовыми метками. SEARCH_RESOURCE_SLOT / RESOURCE_MODE, FIRST_SOURCE и AGENT_FINISHED показывают active/peak/queue, slot wait, режим, отмены, время первого проверенного источника и длительность агента. Старые download/HTML/PDF/LLM/usage события сохранены. search_metrics дополнительно агрегирует ожидание, пик, timeouts/cancel, смены режимов, p50/p95 первого источника и агента. Не логируются URL/ключи/полные документы/сообщения.

В варианте real_trafilatura используется настоящий ресурсно ограниченный child. Это не production benchmark Orange Pi и не живой SearXNG/LLM. Пик HTTP: 1 -> 2; HTML: всегда 1; решений планировщика: 2 -> 2 (реальных LLM-вызовов нет). Event-loop heartbeat продолжал работать во время извлечения.

## Ограничения и готовность

Готово к контролируемому развёртыванию после явного запроса владельца. Нужно проверить коротким smoke-тестом реальные режимы/CPU/memory cgroup после выкладки, а не делать нагрузочный тест. Порог CPU на общей машине может быть консервативным; env позволяет уточнить память/ожидание, отключить comparison batch через WRISTMIND_WEB_COMPARISON_PARALLEL_READ=false.

Физически зависший PDF/OCR поток невозможно принудительно остановить: он удержит один соответствующий слот, а следующие операции получат bounded resource error. Это не новая процессная изоляция PDF; HTML по-прежнему имеет жёсткий memory/time cap. Уже работающий INGEST не прерывается в пользу ANSWER — сохранён существующий последовательный job loop. Альтернативные ссылки, ведущие редиректом на один документ, могут потребовать отдельных первоначальных загрузок. Проверка структуры по-прежнему не доказывает текстологическую подлинность оригинала.
