# Компаньон: установка и обновление часов

Этап 7, SelfHost-копия. Production исходного проекта не меняется.

## Для пользователя

1. Установите APK компаньона из официального релиза WristMind. Сервер должен быть доступен по HTTPS (этап 5).
2. Введите адрес своей панели и одноразовый код из её раздела подключения устройств. Ключ устройства хранится в зашифрованном хранилище телефона.
3. Нажмите «Установить или обновить на часах». Можно установить приложение до подключения сервера, но передача настроек требует подключённого компаньона.
4. Телефон и часы должны быть в одной доверенной Wi-Fi сети и сопряжены в приложении производителя. На часах включите режим разработчика, ADB и беспроводную отладку.
5. Откройте «Сопряжение с кодом», введите IP, **порт сопряжения** и код часов. Это другой код, не код из панели. Затем вернитесь на основной экран отладки и введите **порт подключения**.
6. Мастер проверит тип устройства, Android API, версии и подпись APK. Установка идёт поверх текущего приложения, без очистки его данных. Подтвердите системный запрос на часах, если он появится.
7. Откройте WristMind на часах и нажмите «Передать настройки». Готовность подтверждается ответом часов после проверки ключа на сервере, а не фактом отправки сообщения.
8. Выключите беспроводную отладку после установки.

## Зачем ADB и что делает мастер

ADB нужен только для проверки версии/типа часов, установки APK WristMind и запуска его главного экрана. Мастер не удаляет приложения, не очищает данные и не меняет системные настройки. Он не отправляет код сопряжения на сервер. ADB-ключ шифруется ключом Android Keystore и исключён из резервного копирования. Никаких открытых device-token в ADB shell, логах, UI или сохранённом состоянии экранов.

ADB сам по себе даёт широкий доступ к устройству. Это не обещание абсолютной безопасности: используйте доверенную сеть, проверенный релиз и выключайте отладку после работы. libadb-android не прошла отдельного аудита безопасности; проверка физических устройств входит в финальную приёмку.

## Передача настроек

Новый контракт дополняет существующий `/wristmind/config/v1`, не ломая его:

- Перед ключом ADB запускает целевое приложение с одноразовой публичной UUID-меткой (10 минут). `/wristmind/install/probe/v1` проверяет эту метку на доступных через Data Layer часах. При несовпадении ключ не отправляется. Это связывает ADB-устройство с узлом Wearable Data Layer.
- Адресное MessageClient-сообщение `/wristmind/install/config/v1`: `request_id` UUID, `nonce`, `server_url`, `device_token`.
- Подтверждение `/wristmind/install/ack/v1`: тот же `request_id`, `ok`; без токена.
- Передача допускается только при одном доступном узле `wristmind_watch`. Несколько часов требуют временно отключить остальные, чтобы не переписать чужие настройки.
- Часы проверяют HTTPS URL, а затем авторизацию запросом списка чатов. Только после успеха сохраняют конфигурацию и уведомляют действующий ViewModel. При ошибке прежняя конфигурация остаётся.
- Транспорт защищает Wearable Data Layer; телефон и часы должны иметь один package ID и сертификат подписи. Подтверждение принимается только от целевого node ID с совпадающим request_id.
- Приватное хранилище release-приложения нельзя корректно переписать через `run-as`. Вместо небезопасного ADB fallback остаётся штатный ручной ввод адреса и нового кода на часах.

## Обновления приложений

APK часов встроен в APK компаньона; отдельное хранилище загрузок и серверная команда обновления для этого не нужны. Обновление backend через терминал **не обновляет часы**.

Порядок выпуска:

1. Менять исходники этой копии. Увеличивать `versionCode` отдельно в phone/wear при изменениях соответствующего приложения; `versionName` — видимая версия релиза.
2. Подписывать оба APK неизменным ключом. Хранить keystore отдельно от Git и сервера пользователей. Потеря ключа лишает возможности обновить приложение поверх старого.
3. `:phone:assembleRelease` сначала собирает подписанный Wear APK и включает его в assets. Неподписанный Wear APK сборка компаньона не принимает. Оба сертификата дополнительно сравниваются на телефоне перед установкой.
4. Опубликовать APK компаньона и часов с контрольными суммами в релизе GitHub (публикация/аудит релиза — этап 8). Пользователь обновляет компаньон обычной Android-установкой поверх прежней версии, затем запускает мастер обновления часов.
5. Мастер сравнит установленный `versionCode` с встроенным. Более новая версия на часах не понижается. При несовпадении подписи PackageManager откажется от обновления; мастер не предложит автоматическое удаление или очистку данных.
6. Перед обновлением снова включить отладку. IP сохранён; порт может измениться. Повторное сопряжение требуется, если часы забыли ADB-ключ телефона. После обновления выключить отладку.

Скачивание новой версии и уведомления о ней пока не автоматизированы: новая версия APK часов приходит вместе с новым компаньоном. Это выбранный первый рабочий механизм, а не скрытая серверная автоустановка.

## Сборка разработчика

JDK 21, Android SDK 35. Без Firebase-файла push не регистрируется; чат работает через штатный API/проверку обновлений. Персональные Firebase-ключи не требуются для сборки.

```bash
ANDROID_HOME=/path/to/android-sdk JAVA_HOME=/path/to/jdk21 ./android/gradlew -p android \
  :core:test :wear:testDebugUnitTest :phone:testDebugUnitTest :phone:assembleDebug
```

Release использует игнорируемый `android/local.properties`: `wristmind.signing.storeFile`, `wristmind.signing.storePassword`, `wristmind.signing.keyAlias`, `wristmind.signing.keyPassword`. Не коммитить этот файл или keystore. Адрес пользователя вводится в компаньоне; Wear использует нейтральный placeholder до настройки. Основной проект и его production BuildConfig не меняются.

## Проверка на реальном устройстве — этап 8

- Xiaomi Watch 2: первое сопряжение, неверный код/порт, другой Wi-Fi, смена порта после перезагрузки.
- Установка с подтверждением и отказом, нехватка места, старый SDK/телефон вместо часов.
- Обновление signed release N → N+1: неизменность токена, чатов, черновиков; ошибка иной подписи без потери данных.
- Передача настроек с закрытым/открытым приложением часов, плохой HTTPS/ключ, недоступный сервер, несколько часов; старые настройки остаются при ошибке.
- Проверка direct HTTPS first после отключения отладки и независимой работы часов без телефона; proxy through Wearable Data Layer только fallback.
