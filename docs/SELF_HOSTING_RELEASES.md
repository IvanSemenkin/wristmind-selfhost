# Релизы и обслуживание бесплатного WristMind

Запустите единое меню на сервере и укажите каталог установленной системы:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/IvanSemenkin/wristmind-selfhost/main/install.sh)
```

Все операции установки/обновления/бэкапа/восстановления выполняются **только из терминала**.
Веб-панель не имеет кнопок обновления, административных API для запуска Docker или доступа к shell.
Все сервисы работают на одном собственном сервере: панель, API, база и обработчик задач.
Домен необязателен; HTTPS или туннель настраиваются на том же сервере.
Работаем в WristMind-SelfHost. Основной соседний проект не обновляется этим механизмом.

## Для разработчика: подготовить версию

Изменять существующие модули `web/`, `server/`, `selfhost/`; Компаньон включает совместимый Wear APK; их сборка/постоянная подпись и выпуск описаны в COMPANION_SETUP.md.
Перед выпуском проверить код, проверить переход с предыдущего релиза и заполнить
`RELEASE_NOTES.md` конкретными изменениями и результатами серверной приёмки.

Нумерация X.Y.Z: небольшой фикс — 1.0.1 → 1.0.2, новая совместимая возможность — 1.1.0.
Опубликованную версию не пересобирать и не заменять: для исправления выпускать следующий номер.
Архитектуры: amd64 для обычного VPS/PC, arm64 для подходящих ARM-серверов, включая Orange Pi.

Локальная сборка при доступном Docker:

```bash
python3 selfhost/release.py --version 1.0.1 --arch amd64 \
  --output outputs/wristmind-1.0.1-amd64.tar.gz
```

Команда собирает готовый образ API/worker/панели, фиксирует его ID и зависимости
PostgreSQL/Caddy/cloudflared/SearXNG по digest. Пакет содержит только разрешённые
файлы установщика и образ, манифест и SHA256 каждого файла. Рядом создаётся `.sha256`.
`.env`, пользовательские файлы, токены, бэкапы, приложения Android, legacy-код и Git-история
не входят в архив релиза. Контекст Docker отдельно ограничен `.dockerignore`.
Размер одного публичного пакета ограничен 2 GiB для GitHub Releases.

Для автоматической публикации после подготовки чистого публичного репозитория:

```bash
git tag -a v1.0.1 -m "WristMind 1.0.1"
git push origin v1.0.1
```

Workflow `.github/workflows/selfhost-release.yml` запускает Python-контракты,
web-тесты и сборку, затем независимо собирает amd64/arm64. Только когда обе сборки
успешны, создаёт draft с обоими пакетами и контрольными суммами и публикует релиз.
Существующий релиз не перезаписывает. Неудачный upload может оставить draft:
проверить его вручную, не выдавать его за успешный выпуск. Код, заметки и workflow
должны быть уже включены в тег; сами команды выше не сохраняют незакоммиченные файлы.

**Не публикуйте скопированную Git-историю**: используйте чистый экспорт из [PUBLIC_RELEASE_CHECKLIST.md](PUBLIC_RELEASE_CHECKLIST.md), ручную проверку секретов, выбор
лицензии и итоговая серверная приёмка этапа 8. Сейчас публикация в GitHub не выполнялась.

## Для владельца сервера: установить готовый релиз

Скачать пакет своей архитектуры из доверенного релиза и скопировать SHA256 из
соответствующего `.sha256`. Проверка хеша защищает от повреждения и подмены относительно
известного хеша, но не является цифровой подписью автора. Доверять репозиторию,
автору релиза и источнику самой контрольной суммы.

**В меню выберите:** 5 → 8 «Установить из готового пакета», затем 6 «Ссылка первого входа».


Вместо `--package` можно указать `--url https://...`: скачивание через HTTPS,
переходы на HTTP запрещены, хеш обязателен. Сборка исходников на сервере не требуется.
Меню автоматически подготавливает Docker/Compose и системные зависимости на поддерживаемых Ubuntu/Debian. После первого входа домен/NAT
настраиваются пунктом 4 меню. Неиспользуемые зависимости скачиваются при включении
соответствующей функции; первый запуск и обновление не являются полностью offline.

Ошибка первичной установки сохраняет секреты и файлы. Повторить тот же пакет,
SHA256 и прежний каталог через пункт 5 → 8. Демо предназначено для тестового каталога/ответов без реальных ключей; обычная установка предлагает выбрать этот режим в пункте 3.

## Обновить

**В меню выберите:** 5 → 1 «Версия», затем 5 → 2 «Обновить из пакета».


Либо пункт **5 → Обновить из пакета** в терминальном меню. Перед update:
- Проверяются SHA256 всего архива и каждого файла, формат, безопасные пути, архитектура,
  номер версии и поколение базы. Ссылки, дополнительные файлы, обходы путей и повторная
  установка той же/более старой версии отклоняются.
- Загружается образ и скачиваются фиксированные активные зависимости. Сетевой сбой
  на этом шаге не останавливает прежнюю систему.
- Останавливаются API, worker, Telegram и gateway, если они работали. Создаётся полный
  согласованный бэкап: pg_dump, приватный том с ключами/источниками, конфигурация и прежний образ.
- Применяется новая версия, поднимаются сервисы, проверяется `/health` внутри контейнера.
  Пока переход не зафиксирован, API возвращает 503, WebSocket закрывается с 1013,
  worker не начинает новые платные/фоновые задания. `/health` продолжает работать.
- После проверки снимается режим обслуживания. Ключи, проекты, режимы и чаты сохраняются.

Обновление требует временного перерыва и свободного места под образы, временные файлы
и полный бэкап. Не отправлять новые запросы до окончания операции. Первый переход с
прототипа, образ которого ещё не содержит maintenance-boundary, проверять отдельно;
полноценная защита от новых запросов во время health-проверки работает в выпущенных образах.

При сбое после бэкапа предпринимается восстановление прежних настроек, образа,
базы и приватных файлов. Если Docker/диск также мешают откату, журнал сохраняет
путь и хеш бэкапа, следующие обновления блокируются до восстановления. Прерывание
во время бэкапа можно отменить через rollback, запустив прежние сервисы.

## Резервная копия, ручное восстановление и откат

**В меню выберите:** 5 → 4 «Бэкап», затем 5 → 6 «Откат», затем 5 → 5 «Восстановить бэкап», затем 5 → 1 «Версия».


Имя проекта выводит `version`. **Restore и rollback заменяют текущие данные состоянием
из выбранной копии**: более новые сообщения/файлы будут потеряны. Поэтому требуется
точное подтверждение имени проекта. Обычный restore сначала создаёт ещё одну копию
нынешнего рабочего состояния. Если текущая система повреждена и не может сделать
эту копию, нужен аварийный режим восстановления; обычное меню откажется обходить защитную копию. Обязательный бэкап перед update этим
параметром отключить нельзя.

Бэкапы находятся в `backups/` выбранной установки, каталог 700, архив 600. В них есть
ключи и приватные материалы: не публиковать, переносить только по защищённому каналу,
хранить отдельную зашифрованную копию вне сервера. Сам архив не зашифрован.
Сертификаты Caddy не включены: при восстановлении на новом сервере Caddy получает их
заново; учитывать DNS и лимиты центра сертификации. Все тома существующей установки
сохраняются. Автоматической ротации/удаления резервных копий нет.

На новом сервере restore поддерживает пустой каталог, восстанавливает исходные
ключи и имя проекта. На том же Docker-host нельзя создавать второй живой экземпляр
с этим именем: сначала убрать старые контейнеры, сохранив тома. Если восстановление
само завершилось ошибкой, журнал показывает точку возврата/повторной попытки;
повторять через rollback после исправления причины. Rollback также требует подтверждения.

## Миграции и безопасное удаление

Текущие релизы: schema=1, PostgreSQL 16. Существующие совместимые изменения базы
применяются текущим init_database при старте API. Смена поколения схемы или major
PostgreSQL автоматически запрещена. Для такого релиза понадобится отдельная
протестированная миграция; нельзя просто поменять поле schema в манифесте.
Для rollback восстанавливается база вместе с образом, а не только старый контейнер.

**В меню выберите:** 5 → 7 «Удалить контейнеры».


Удаляет контейнеры/сеть этого Compose-проекта, **без `-v`**. Чаты, тома, конфигурация,
источники и резервные копии остаются. Не вызывает Docker prune и не удаляет чужие
контейнеры. Обслуживание блокируется тем же lock, что установка и настройка домена.

## Результаты локальной проверки

Архивы, SHA256, разрешённый состав релиза, консистентные копии, отказ до изменения
данных, секреты, переключение версии, автоматический/ручной откат, прерванные операции,
холодное восстановление, resume и maintenance-boundary проверяются тестами.
Docker-операции восстановления моделируются; код распаковки приватных файлов
дополнительно выполняется в настоящем локальном Python на тестовых данных.
Реальные pg_dump/pg_restore, сборка/запуск образов, обновление PostgreSQL, работа
GitHub workflow, HTTPS после обновления и переход между двумя настоящими релизами
ещё требуют итоговой серверной приёмки. Без этого выпуск пользователям не подтверждён.

## Ночное расписание (0.3.1+)

Терминальное меню **5 → 3**: включение, изменение времени/часового пояса и отключение. По умолчанию расписание выключено. Системный timer использует IANA timezone в OnCalendar и Persistent=false; пропущенное время не догоняется днём. На одном сервере разные каталоги установки получают отдельные timers.

Перед обновлением проверяются задания ANSWER/INGEST и другие queued/running jobs; проверка повторяется после загрузки и перед резервным копированием с закрытием приёма новых запросов на время финальной проверки. Выполняется существующий update --latest с обязательным бэкапом и health/rollback. Если проверка недоступна или есть активная работа, данные не обновляются. Расписание не установлено автоматически на сервере разработчика или тестовом сервере.

Файл .wristmind-auto-update.json хранит локальный выбор пользователя, не содержит секретов и сохраняется при обычном обновлении. Он и системные unit-файлы не входят в переносимый бэкап: после восстановления на другой сервер включите расписание через меню. При откате к версии старше 0.3.1 отключите timer через свежий установщик.
