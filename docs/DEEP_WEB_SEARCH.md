# Глубокий веб-поиск: выбор источников и завершение

Реализовано локально 12 октября 2026 года. Production и GitHub этим этапом не обновлены.

## Проверенная исходная последовательность

`worker.process_answer()` сохраняет маршрутизацию запроса, постановку задачи,
уточнение коротких отсылок и решение о рабочем источнике. Затем
`run_search_agent()` получает выдачу; раньше перед каждым open/find/read/search/answer
вызывался `choose_web_action()`. Сохранение принятого источника сразу останавливало
цикл. Ошибочный JSON или недоступная модель планировщика превращались в `answer`.

В новом цикле:

- Первый самостоятельный запрос в чате с точным названием в кавычках и целью «полный текст»
  или номером раздела не требует `choose_contextual_search_query()`. Последующие сообщения и уточнения
  «тот», «прежний», «другой», «вместо» сохраняют контекстный путь.
- `search_web()` ранжирует до отсечения выдачи до прежнего лимита. Обрабатываются
  первые 100 результатов уже полученного JSON; дополнительных запросов нет.
- Учитываются совпадения слов и названия, явно заданный автор с инициалами,
  номера разделов, указания оригинала/полного текста, признаки типа источника.
  Краткие пересказы и готовые ответы понижаются, если пользователь не ищет их.
  Институциональный домен — лишь небольшой бонус, не разрешающий список.
- Единственный уверенный лидер с точным названием, автором (если указан),
  пометкой полного оригинала и достаточным отрывом может открываться без LLM.
  При близких оценках, сложной постановке или сравнении выбор остаётся агентным.
- Для явно указанного количества глав проверяется весь извлечённый документ:
  отдельные заголовки, арабские/римские номера и минимум 80 символов текста главы.
  Для конкретного раздела проверяются заголовок и наличие текста после него.
  Эти проверки не устанавливают подлинность и отсутствие купюр внутри разделов.
- Сравнение требует минимум двух различных URL. Перенаправления на один URL
  не считаются двумя материалами. Два URL сами по себе не гарантируют независимость
  авторов; смысловые противоречия разбирает модель ответа по обоим фрагментам.
- После сохранения одного рабочего источника дополнительные страницы читаются для
  проверки. Повторная классификация/извлечение рабочего источника не запускается.
  Если явно заданное число глав не подтверждено, кандидат не сохраняется как
  полный оригинал; это не затрагивает ранее созданные пользовательские источники.
  Временные документы остаются в обычном кэше, без embeddings и INGEST.

## Ошибки и ограничения

`PlannerFailure` отличает невалидную схему/JSON, неверный ID и отказ модели от решения
«доказательств достаточно». Агент пытается прочитать следующий подходящий кандидат
в прежнем бюджете; если его нет, возвращает незавершённое состояние. Повторные
действия и поисковые запросы не повторяют платные/сетевые операции бесконечно.
Ошибочный диапазон чтения получает диагностику для следующего решения модели.

HTTP-ошибки и пустой извлечённый текст помечаются ошибкой источника. Недоступные
движки SearXNG сохраняются как предупреждение частичной выдачи. Пустая выдача,
ошибка чтения или истечение бюджета не являются доказательствами отсутствия данных.
Модель ответа получает состояние, причину остановки и результаты проверок.

`SearchOutcome.completion` и `message.meta.web_search.completion`:

| Значение | Смысл |
| --- | --- |
| `success` | Цикл завершён с прочитанными материалами; обязательные проверки выполнены, предупреждений/ошибок нет. Область структурной проверки указана в `checks.scope`. |
| `partially_verified` | Есть фрагменты/прочитанные материалы, но проверка неполна либо были ошибки/предупреждения. Быстрый поиск по сниппетам также имеет этот статус. |
| `limits_exhausted` | Закончились время, шаги, открытия/запросы либо агент повторяет действия без прогресса. |
| `source_error` | Не удалось прочитать ни один документ, есть ошибки страниц. |
| `search_error` | Поиск/планировщик недоступен, выдача пуста, пригодных прочитанных данных нет. |

Метаданные дополнены `stop_reason`, `planner_calls`, `planner_ms`,
`deterministic_steps`, `explicit_query`, `warnings`, `checks`, `ranking` с причинами
оценок. Это счётчик вызовов именно планировщика, а не всех вызовов провайдера за ответ.
Маршрутизатор, построение постановки, классификация/извлечение рабочего источника,
основной ответ и research-review сохраняются. Общие типы API не изменены;
`WebSearchResults` совместим с прежним списком результатов.

## Ресурсы и границы

Новый worker не добавлен. Сетевые операции последовательны; лимиты поиска,
страниц, скачивания, памяти/таймаута HTML и фрагмента модели остаются прежними.
Проверка использует уже извлечённый текст, не вызывает локальных моделей.
SSRF, перенаправления и ограничение загрузки остаются в `open_web_page()`.
PDF-обработка и хранение/индексация пользовательских рабочих источников сохранены.

Автоматический выбор намеренно узкий. Необычная разметка, главы словами,
неуказанное количество глав, сложные авторские отсылки и неоднозначные названия
могут сохранить дополнительные решения модели или завершиться частично.
Чтение JavaScript, обход 403 и объединение книги из отдельных страниц не добавлены.

## Локальное сравнение скорости

Сохранённый до изменения `search_agent.py` сравнивался с новым циклом в пяти
запусках одного сценария: полный текст «Капитанской дочки» с 14 главами,
однозначная выдача, без записи рабочего источника. Обе версии сделали один
поисковый запрос и одно открытие. В старом цикле — два решения планировщика,
в новом — ноль. Сеть и модель имитированы: открытие 3 мс, решение модели 25 мс.
Медиана локального цикла: **62,78 мс → 8,34 мс**. Это измерение синтетического
сценария и стоимости исключённых решений, а не фактическая задержка DeepSeek,
SearXNG или Orange Pi. Изменений реальной нагрузки на сервере не измеряли.

Воспроизводимый сценарий — `server/tests/benchmark_search_agent.py`.
Без `--baseline` он сравнивает включённые/выключенные эвристики в текущем коде.
Для сравнения с прежним циклом передайте `--baseline` с доверенной сохранённой
копией старого `search_agent.py`. Скрипт не обращается к сети или БД.

## Проверки этапа

- 17 новых сценариев: полный литературный текст, отсутствующая глава/раздел,
  далеко расположенный раздел, противоречащие источники, HTTP/пустое извлечение,
  JSON/Markdown планировщика, повтор действий, частичная/нерелевантная выдача,
  таймаут, неправильный автор, неоднозначные кандидаты и неполный первый оригинал.
- Финальная проверка нового набора и API-worker: **18 passed**.
- PDF с отказом первой страницы, сохранением рабочего документа и последующим
  INGEST/RAG прошёл после изменения теста: кандидат выбирается по URL, а не старому
  порядку SearXNG. Проверяется HTTP 413 и `partially_verified`.
- Расширенный прогон: **109 passed**; две выявленные проблемы затем закрыты и
  перепроверены: слабое совпадение русской формы слова в сравнении (короткие основы)
  и устаревший порядок кандидатов в PDF-тесте. В дополнительном наборе — 26 passed,
  затем PDF-тест с исправленной сигнатурой mock и весь новый набор прошли.
- SelfHost: 20 passed (поисковые сценарии и веб-защиты), отдельно 2 passed
  (API-worker и PDF → рабочий источник → INGEST). Общие функции сверены;
  отдельный внешний search API и feature/runtime-настройки сохранены.
- Два существующих предупреждения Starlette/anyio о deprecated API. Полный
  backend-suite, production PostgreSQL и реальные провайдеры этим этапом не проверялись.
