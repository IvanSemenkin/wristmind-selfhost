# Диагностика и кэш веб-поиска — этап 3

12 октября 2026. Изменения локальные; рабочий сервер и GitHub не обновлялись.

Предыдущие этапы проверены по коду: полный HTML хранится отдельно от модельного фрагмента; извлечение ограничено размером, временем и памятью дочернего процесса. Есть чтение дальних разделов, ранжирование результатов, проверка структуры книги и состояния частичного результата/ошибки/лимитов. Временное открытие не создаёт embeddings. Один worker сохранён.

## Что изменилось

Раньше существующие latency-события показывали некоторые общие этапы, но не объединяли назначения всех LLM-вызовов, извлечение, кэш и итог поиска. Теперь `search_trace.py` добавляет в тот же ротируемый JSONL события `SEARCH_STAGE`, `SEARCH_LLM`, `SEARCH_CANDIDATE`, `SEARCH_RESULT_REJECTED`, `SEARCH_SOURCE_ERROR`, `SEARCH_SOURCE_REJECTED`, `SEARCH_CACHE`, `SEARCH_FINISHED`, `SEARCH_SUMMARY`, предупреждения агента/частичной выдачи.

- SearXNG, скачивание (включая ошибки), HTML extraction, собственно trafilatura, PDF extraction/text layer: длительности и размеры. trafilatura сообщает метрики из ограниченного дочернего процесса, отдельно от запуска процесса/ожидания слота. Ошибки открытия имеют тип ошибки и HTTP-код, когда он доступен.
- LLM: назначение, длительность всего потребления потока, число логических вызовов/сетевых попыток, `usage`, если оно уже приходит от API. Назначения включают маршрутизацию, якорь запроса, планировщик, выбор фрагмента, проверку источника, пересмотр/исправление ответа и OCR. Вложенные обёртки не удваивают счётчик. Запросы к провайдерам не изменены ради получения usage; отсутствующие токены не считаются нулевыми.
- Итог: поиски, попытки открытия, успешные чтения, подтверждённые источники, причина завершения, кэш. Отмена сохраняет уже выполненные счётчики, прерывает сетевое действие и не запускает сохранение источника.
- Записываются RSS/peak RSS родительского процесса и peak RSS HTML-процесса. Это снимки/пиковое значение процесса, а не точное выделение памяти конкретного документа.

Новые события принимают только разрешённые числовые поля и короткие коды. Нет запросов, заголовков, текстов, путей, API-ключей, тела исключений или URL: URL представлен SHA-256 fingerprint. Убрана печать сырого ответа маршрутизатора в предупреждениях. Новые события не включены в список отправки Telegram. Ошибка диагностики не останавливает поиск.

`process_next_job()` больше не отменяет наблюдателя в середине закрытия его DB-сессии. Наблюдатель просыпается при завершении answer-task; это устраняет обнаруженную локальными тестами гонку закрытия SQLite. Запись времени использования кэша перенесена из чтения в завершающую транзакцию, чтобы поиск не держал SQLite write-lock во время публикации событий.

## Актуальность и ограничения кэша

Раньше пригодность зависела от версии извлечения/размера и явного требования свежести. Теперь есть `last_checked_at`, `last_accessed_at`, `cache_kind`, `cache_bytes`; добавление nullable-колонок идемпотентно, без удаления/перезаписи старых данных. Старые записи используют `retrieved_at`; версия извлечения 0 требует повторной загрузки и не выдаётся за полный документ.

| Тип | TTL по умолчанию | Переменная окружения |
|---|---:|---|
| Новости | 1 час | `WRISTMIND_WEB_CACHE_NEWS_TTL_SECONDS` |
| Обычная страница | 1 сутки | `WRISTMIND_WEB_CACHE_PAGE_TTL_SECONDS` |
| Документ/PDF | 7 суток | `WRISTMIND_WEB_CACHE_DOCUMENT_TTL_SECONDS` |
| Статическое произведение | 90 суток | `WRISTMIND_WEB_CACHE_STATIC_TTL_SECONDS` |

Тип определяется консервативной эвристикой заголовка/пути/глав; это не гарантия неизменности оригинала. Ноль отключает повторное использование соответствующего типа. Явный запрос свежести обходится без кэша. Чтение не продлевает TTL. При неудачном обновлении старые данные сохраняются, но не становятся свежими.

Обновление сохраняет `id`, исходные `content`/`content_hash` и provenance; актуальная версия — `full_content`. Рабочие файлы, выбранные фрагменты, KnowledgeSource и существующие chunks не изменяются, переиндексация не запускается. Кэш хранит первоначальный и последний текст, а не журнал всех промежуточных версий.

Общий бюджет **непривязанных временных записей**: 512 записей и 64 000 000 байт (`WRISTMIND_WEB_CACHE_MAX_ENTRIES`, `WRISTMIND_WEB_CACHE_MAX_BYTES`). При заполнении новая страница остаётся доступной в текущем поиске, но не добавляется в кэш. Проверяется SQL-агрегат метаданных, без загрузки всех текстов. Для неизвестного размера старой записи резервируется консервативный объём. Уже существующие данные не удаляются ради квоты; уменьшение записи разрешено. Записи, связанные с KnowledgeSource, и явно сохраняемые рабочие источники защищены от отказа по этой квоте. Пользовательское хранилище поэтому не ограничивается бюджетом временного кэша.

## Лёгкие метрики

Из каталога `server/`:

```bash
python -m wristmind_server.search_metrics
```

Используется существующий `latency_trace` path. Для другого локального JSONL: `--path /path/to/trace.jsonl`. Чтение ограничено последними 4 MB / 5000 событий; новые сервисы или базы не нужны. По умолчанию трассировка включена; существующее `WRISTMIND_LATENCY_TRACE_ENABLED=false` отключает запись.

Результат: p50/p95 времени полного ответа отдельно web/deep_web, среднее число LLM-вызовов, доля успешных открытий, доля завершённых поисков без подтверждённого источника, cache hit ratio, пропуски из-за квоты, этапные p50/p95, память и возвращённые токены. Полное время включает очередь/работу worker до завершения ответа. Быстрый поиск по snippets учитывается как поиск без открытого подтверждённого документа, даже если ответ полезен. Отмены учитываются отдельно, исключены из response percentiles. Usage может быть неполным по провайдерам; сумма обозначена `total_tokens_reported`.

Это окно последних событий, а не исторический мониторинг. Ротация и ограничение окна могут исключить начало отдельных трасс. Поле `n` обязательно учитывать; при отсутствии измерений возвращается `null`.

## Локальные измерения до/после

Сравнение с сохранённым кодом **начала этого этапа**, после предыдущих двух этапов. Ноутбук, без Orange Pi, без внешнего поиска/LLM. HTML извлечён реально; SearXNG — HTTP MockTransport, страницы агенту даны фикстурами. Для HTML использован прежний дочерний parser отдельно от нового. Порядок before → after, небольшие выборки, nearest-rank p95.

| Проверка | n на вариант | До p50 / p95, ms | После p50 / p95, ms |
|---|---:|---:|---:|
| HTML, 1 050 427 входных символов | 5 | 243,619 / 249,449 | 239,926 / 247,347 |
| SearXNG через MockTransport | 7 | 0,321 / 2,173 | 0,410 / 0,534 |
| Быстрый агент, без ответа LLM | 7 | 0,308 / 0,373 | 0,416 / 0,522 |
| Глубокий агент, все 14 глав | 7 | 3,791 / 6,387 | 4,245 / 4,501 |

Извлечение в обоих вариантах вернуло 1 050 235 символов; тестовый лимит задан 1 100 000, память parser — 256 MB. RSS родителя в измерении — 49 184 768 B; пик HTML child — 54 321 152 B. Быстрый агент: 1 поиск, 0 открытий, 0 planner LLM-вызовов. Глубокий: 1 поиск, 1 открытие, 0 planner LLM-вызовов; структура подтверждена. Число вызовов не изменилось этим этапом. Отдельный тест реального адаптера с HTTP-моком проверяет 1 логический LLM-вызов и usage 11 input + 3 output = 14; это тестовые данные, не расход реального API.

Ориентиры прежних живых замеров: SearXNG 2,24 s; быстрый поиск 11,37 s; глубокий 35,03 s. Новых живых end-to-end замеров нет. Их нельзя сравнивать с миллисекундами mock-теста. Ускорение на сервере **не подтверждено**; небольшая добавочная цена диагностики ожидаема.

## Проверки и границы

Результаты целевых прогонов фиксируются в CURRENT_STATE.md. Проверены локальные HTTP-моки, обычный/длинный HTML, повреждённый HTML, дальние/отсутствующие разделы, PDF с текстом/сканами, 30-страничный PDF, ограничения размеров/памяти/таймаута, HTML semaphore, JSON/repeated planner, сравнение источников, частичная выдача, кэш/старый SQLite schema, неизменность рабочих источников, сохранение и вопросы по сохранённым документам, отмена и приватность метрик.

Осталось: фактические p50/p95 на Orange Pi после выкладки; проверка PostgreSQL migration на тестовом экземпляре (локально проверен SQLite); ограниченное покрытие usage у разных API; эвристическая классификация TTL. Квота не очищает уже разросшийся исторический кэш и не ограничивает пользовательские рабочие источники. PDF extraction остаётся в существующем thread/text-layer пути, без нового жёсткого лимита адресного пространства как у HTML. Структурная проверка глав не доказывает литературную подлинность. Нагрузочных/сетевых тестов на сервере не выполнялось.
