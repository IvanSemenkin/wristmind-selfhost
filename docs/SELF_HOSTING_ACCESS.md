# Домен, HTTPS и доступ за NAT

Этап 5 работает в пользовательской копии. Основной production не затрагивается.
Домен необязателен: установка сначала запускается локально. В интерактивном терминале
после установки предлагается настроить внешний доступ или пропустить. Вернуться к
настройке можно через пункт 4 меню `./wristmind` или команду `access`.

## Локально, без домена

```bash
./wristmind install --install-dir /opt/wristmind
./wristmind setup-link --install-dir /opt/wristmind
```

HTTP-порт по умолчанию доступен только на самом сервере. Для настройки с ноутбука
можно использовать SSH-перенаправление:

```bash
ssh -L 8080:127.0.0.1:8080 user@server
```

Затем открыть `http://localhost:8080/setup`. Это позволяет настроить панель без домена;
внешний доступ и подключение устройств по HTTPS настраиваются отдельно.
Одноразовую ссылку активации не публиковать. При возврате к локальному режиму ранее
сохранённая браузером Secure-cookie может потребовать повторного входа.

## Свой домен на сервере с публичным IP

1. Создать DNS-запись A на IPv4 сервера. Если есть AAAA, она также должна указывать
   на этот сервер. Для этой проверки использовать DNS-only, без проксирования Cloudflare.
2. Открыть входящие TCP 80 и 443 на сервере и, при необходимости, маршрутизаторе.
   CLI не меняет firewall и настройки роутера.
3. Выполнить настройку в терминале или одной командой:

```bash
./wristmind access --install-dir /opt/wristmind
./wristmind access --install-dir /opt/wristmind --mode domain \
  --domain ai.example.org --expected-ip 203.0.113.10
```

Для нескольких IP использовать `--expected-ip 203.0.113.10,2001:db8::1`.
Проверяются все найденные A/AAAA; несовпадение или отсутствие DNS останавливает
настройку до изменения файлов. Нельзя использовать IP, URL, wildcard или путь вместо домена.

Можно сразу указать домен при установке:

```bash
./wristmind install --install-dir /opt/wristmind \
  --domain ai.example.org --expected-ip 203.0.113.10
```

Сначала завершается базовая установка, затем настраивается доступ; неудача второго
шага сохраняет базовую установку. Для повторной настройки достаточно `access`.

Caddy принимает HTTP/HTTPS, автоматически получает и продлевает сертификаты,
перенаправляет HTTP на HTTPS и передаёт запросы панели/API в существующий контейнер.
Сертификаты сохраняются в отдельных томах данного Compose-проекта. Стриминг не
буферизуется; WebSocket поддерживается существующим reverse proxy.
Основание: [Caddy Automatic HTTPS](https://caddyserver.com/docs/automatic-https),
[reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).

## За NAT: Cloudflare Tunnel

Публичный входящий IP и открытие портов не нужны. Нужен домен в аккаунте Cloudflare:

1. Создать remotely managed Tunnel в Cloudflare.
2. Добавить public hostname, например `ai.example.org`, с service **HTTP → `api:8000`**.
   DNS и маршрутизация управляются аккаунтом Cloudflare; CLI не получает ключ аккаунта
   и не меняет эти настройки вместо владельца.
3. Сохранить токен туннеля в файл с правами `600`, вне исходников и Git.
   Не передавать токен параметром команды, чтобы он не попал в историю shell.
4. Запустить:

```bash
./wristmind access --install-dir /opt/wristmind --mode tunnel \
  --domain ai.example.org --tunnel-token-file /secure/path/tunnel-token
```

Токен копируется в закрытый файл установки и передаётся cloudflared через read-only
mount и `--token-file`; его нет в Compose, аргументах процесса или выводе CLI.
Cloudflared устанавливает исходящее соединение; публичный HTTPS завершается на Cloudflare.
Долгие SSE-ответы дополнительно проверить на настоящем туннеле в итоговой приёмке.
Основание: [Cloudflare Tunnel](https://developers.cloudflare.com/tunnel/get-started/),
[token-file](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/run-parameters/).

## Состояние, повторный запуск и восстановление

```bash
./wristmind access --install-dir /opt/wristmind --mode check
./wristmind setup-link --install-dir /opt/wristmind
./wristmind access --install-dir /opt/wristmind --mode local
```

`setup-link` использует сохранённый публичный адрес. `access --mode check` проверяет
API внутри контейнера и публичный `/health` с обычной проверкой TLS-сертификата,
без перехода по редиректам. Пока сертификат/DNS/туннель не готовы, статус **pending**,
код выхода 1; конфигурация остаётся запущенной. Проверку можно повторить позже.
Это также покрывает невозможность проверить свой публичный адрес изнутри сети
без NAT loopback: окончательно проверить доступ с внешнего устройства.

При ошибке Compose или внутреннего health восстанавливаются прежние файлы и
предпринимается перезапуск прежней конфигурации. Если Docker также не позволяет
восстановить контейнеры, CLI явно сообщает это. Данные, пароли, ключи, чаты и тома
не удаляются. Настройка блокируется во время другой установки/операции доступа.
Возврат к local останавливает только gateway данного проекта; сертификаты и
закрытый токен сохраняются, не очищаются автоматически.

API в обоих внешних режимах принудительно привязан к `127.0.0.1` на хосте.
Forwarded-заголовки доверяются контейнерам собственной Docker-сети, публичный
доступ идёт через gateway. Не подключать посторонние контейнеры к этой сети и
не менять привязку API на публичную при такой конфигурации.

## Проверки до пользовательского релиза

Локально проверяются DNS-контракты, безопасные файлы, сохранение секретов,
переключение режимов, rollback, ссылка активации и настоящий `docker compose config`.
Фактический запуск gateway, выпуск/продление сертификата, внешний HTTPS,
поведение мобильной сети/часов и NAT будут проверены на сервере в этапе 8.
Теги `caddy:2` и `cloudflare/cloudflared:latest` пока являются upstream-тегами;
фиксация версий артефактов относится к этапу 6.
